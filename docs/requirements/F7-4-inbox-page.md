# REQ-F7-4：消息中心页（收件箱消息聚合视图）

> 需求文档（2026-10-10 建立，F7-2/F7-3 真机验收时用户提出，留给下一个 agent 实现）。
> 关联：[F7-2](F7-2-android-webview-shell.md) / [F7-3](F7-3-app-experience.md) /
> [STATUS.md](../STATUS.md) 第四节 F7。

## 背景与目标

收盘日报、异动提醒等推送型消息目前**只有一个出口：聊天页**。机制是
`/api/inbox` 的 drain 语义——聊天页每 30s 轮询一次，取走（服务端随即删除）
所有未读消息，追加为聊天窗里的机器人消息，App 壳再桥接弹系统通知。

真机验收（2026-10-10，Vivo V1838A）暴露两个体验缺口：

1. **消息混在对话流里**：推送消息与问答交错，无法单独翻阅"我收过哪些提醒"，
   聊天一多就被淹没。
2. **离开聊天页看不到**：drain 只有聊天页一个轮询者，消息中心缺失；且 drain
   即删除，消息**没有历史可回查**。

**目标**：新增独立**消息中心页**（`/inbox`），聚合展示收件箱消息（按时间倒序、
含已读/未读状态），聊天页与 App 通知的现有行为不变。浏览器与 App 内都可用
（纯网页端实现，App 壳零改动）。

## 范围

### 做

1. **存储层**（`src/storage/store.ts`）：收件箱消息从"drain 即删"改为
   "归档保留"——至少保留最近 N 条/最近 M 天（具体上限实现时定，参考 inbox
   现有的每用户 100 条上限思路，注意不要无限膨胀）。
2. **API 层**（`src/channels/webchat.ts`）：
   - `GET /api/inbox/history`：非破坏拉取（不删除、不置读），带分页或
     最近 N 条 + 未读数；
   - `POST /api/inbox/read`（或 `?markRead=...`）：标记已读；
   - 现有 `GET /api/inbox`（drain）**保留不动**，聊天页与 F7-3 桥接继续
     走它。
   - 已读状态的落点由实现 agent 定（每条消息 read 标记 vs 用户级
     read_cursor），二选一并在文档中说明取舍；必须与 drain 流程自洽
     （drain 取走的消息应视为已读，否则会出现"聊天里看过、消息中心
     还显示未读"的矛盾）。
3. **前端**：
   - 新静态页 `public/inbox/index.html`：消息列表（时间倒序、未读高亮、
     文本一律 textContent 渲染）、未读数徽标、进入页面即拉取并可手动刷新；
     复用 theme.css / auth.js / compat.js；
   - 导航入口：聊天页与各数据页页头加"消息"入口（参照现有页头导航模式；
     未读数显示与否由实现 agent 定，首版可以只在消息中心页内显示未读数）；
   - 聊天页 drain 行为不变（消息仍进聊天窗 + 桥接弹通知）。

### 不做（明确排除）

- **不改 App 原生壳**（android/）：通知仍由聊天页桥接触发；
  真后台推送（厂商推送通道）维持 REQ-F7-3 既定决策，不做。
- **不做服务端主动推送**（WebSocket/SSE 等），消息中心用轮询即可
  （30s 级，与现有 drain 同节奏）。
- 不做消息分类/筛选/搜索、单条删除、跨设备已读同步（首版聚合列表即可）。
- 不改动现有 `/api/inbox` drain 语义（防多页抢消息的机制不能破坏）。
- 不动收件箱消息的产生方（scheduler / pushInbox 调用方零改动）。

## 功能需求

| # | 需求 |
|---|---|
| FR-1 | `/api/inbox/history` 返回当前用户最近的消息（时间倒序），响应含未读数；**不删除**服务端消息 |
| FR-2 | 标记已读后未读数归零；drain 取走的消息必须视为已读（不得出现两处未读状态矛盾） |
| FR-3 | 消息中心页加载即展示列表；新消息到达后 30s 内（下一轮询）可见 |
| FR-4 | 聊天页现有行为零回退：消息照进聊天窗、App 照弹系统通知 |
| FR-5 | 浏览器直接访问 /inbox 也可用（与 App 内一致）；未登录走现有 auth 浮层 |
| FR-6 | 消息文本一律 textContent 渲染（防注入，项目红线） |

## 非功能需求

- 存储增长有界：归档保留策略必须带上限（条数或天数），不得无限累积。
- 轮询节奏与现有 drain 同级（约 30s），不引入更短周期。
- 纯网页端实现，App 壳、data-service 零改动。
- 兼容旧 WebView：新页面禁用 Chrome 86+ API（见 PITFALLS"前端 / 安卓 WebView"
  节；必须用时先扩 [public/shared/compat.js](../public/shared/compat.js)）。

## 数据模型 / API / 前端改动

- `src/storage/store.ts`：inbox 表加已读标记（或 kv 存 read_cursor）+
  drainInbox 改造（取走=已读）+ history 查询方法。
- `src/channels/webchat.ts`：新增上述两个端点（挂现有 session 鉴权后）。
- `public/inbox/index.html`（新）+ 各页页头导航加入口。
- 迁移注意：存量库 inbox 表无已读列，加列需给默认值（视为已读，避免
  老消息全亮未读）。

## 验收标准

1. `npm run typecheck` + `npm test` 全绿；新端点补单测（history 不删除、
   drain 后 history 仍可见且未读自洽、未登录 401）。
2. 端到端：pushInbox（或等收盘日报）→ 聊天页收到 + App 弹通知 + 消息中心
   可见该条且状态正确；标记已读后未读数归零。
3. 聊天页与消息中心同时打开不互抢消息（消息中心不得调用 drain 接口）。
4. 真机（Chrome 83 WebView）上消息中心页正常渲染。

## 审计要点

- **drain 语义不可破坏**：`/api/inbox` 仍只允许聊天页轮询；消息中心
  必须走非破坏接口。出现"两个页面轮询同一 drain 接口"直接打回。
- 已读状态与 drain 的自洽性（见 FR-2）：重点审查边界——先开消息中心
  后开聊天页、两个页面同时开、App 杀进程重开等场景。
- 归档增长有界：审查保留策略与清理逻辑，确认无无限膨胀。
- 文本渲染全部 textContent，无 innerHTML 拼接消息内容。
- 兼容层：新页面若引入 Chrome 86+ API 而未扩 compat.js，打回。
